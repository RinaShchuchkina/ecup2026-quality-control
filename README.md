# Контроль качества: смесь ветвей на двух категориях

Решение задачи о том, соответствует ли карточка товара заявленной категории.
Проверяются две категории — «БАД» и «Легковоспламеняющиеся»; на входе название,
описание и фотографии товара. Метрика — macro F1: F1 по классу `label=1` внутри
каждой категории, затем среднее по двум.

Публичный лидерборд: **0.882858**. Приватный результат: **0.8679302239**,
четвёртое место из 144 команд.

## Данные

12971 товар. «БАД» — 7469 карточек, позитивов 74.6%. «Легковоспламеняющиеся» —
5502 карточки, позитивов 198, то есть 3.6%.

Это две разные задачи под одной метрикой. БАД почти сбалансирован и решается
текстом: маркировка «БАД», «биологически активная добавка», упоминание СГР почти
всегда есть в описании или на упаковке. ЛВ — редкий класс: половина итоговой
метрики держится на 198 позитивах, а решает часто не текст, а комплектация,
видимая только на фотографии, — есть ли в коробке уголь, газовый баллон или
спички. Отсюда вся асимметрия решения: разные веса ветвей, разные пороги,
отдельная визуальная модель и отдельные правила только для ЛВ.

## Устройство
<img width="577" height="594" alt="image" src="https://github.com/user-attachments/assets/7ea665c6-97da-498c-826d-e3da853fb302" />

Четыре независимых источника вероятности, взвешенная смесь, затем детерминированные
переопределения и порог по категории.

1. **Текстовая ветвь.** TF-IDF плюс логистическая регрессия, отдельная модель на
   каждую категорию. Признаки: слова и биграммы (до 60 000), символьные `char_wb`
   3–5-граммы (до 100 000) и 14 бинарных флагов по регулярным выражениям
   (`биологически активн`, `не является лекарств`, `баллон не входит`,
   `тёрка для поджига`, `пиротехнич` и т. д.), умноженных на 2.0.
   `LogisticRegression(C=4, class_weight="balanced")`.
2. **Мультимодальная ветвь.** LoRA поверх `Qwen3-VL-2B-Instruct`, до 4 фотографий,
   бюджет 3072 токена, 262144 пикселя на изображение.
3. **Текстовая LLM-ветвь.** LoRA поверх `Qwen3.5-4B`, только текст, бюджет
   2048 токенов.
4. **Визуальная ветвь.** EVA-02 base, 5 фолдов, только категория ЛВ. Скоры пяти
   моделей усредняются по фотографии, затем по товару (до 5 фотографий).

Обе LLM-ветви работают без генерации. В системный промпт кладутся правила
категории, вопрос требует ответа одним словом, а вероятность берётся как softmax
по двум логитам — токенов «да» и «нет» — на последней позиции. Один forward на
карточку вместо декодирования; на обучении маскируются все токены, кроме ответа.

Смешивание идёт в два уровня, и это важно для чтения конфигов. Сначала внутри
категории считается `p = (w_text·p_text + Σ w_i·p_i) / Σw`, где `w_text = 1 − Σ w_i`,
а `w_i` — веса LLM-ветвей из `vlm_weights`. Затем визуальная ветвь подмешивается
поверх результата: `p = (1 − w_eva)·p + w_eva·p_eva`. То есть числа из
`vlm_weights` — доли внутри первого уровня, а фактические доли получаются
умножением на `1 − w_eva`. Раннер печатает фактические доли живых ветвей отдельной
строкой, чтобы конфиг не приходилось пересчитывать в уме.

После смеси применяются переопределения, строго в этом порядке: правило
«не является БАД», точный retrieval по текстовым ключам, dHash по фотографиям,
семантический роутер ЛВ. Каждое выставляет вероятность в край шкалы — 0.01 или
0.99, а точный retrieval ровно 0.0 или 1.0 — и снимает карточку с решения модели.
Карточка, уже закрытая retrieval, дальше не переопределяется.

Точный retrieval — это индексы, построенные по обучающей разметке: нормализованное
«название + описание», название без цифр и первые пять слов названия. Совпадение
даёт голоса-метки; переопределение срабатывает только при единогласии (среднее
ровно 0.0 или 1.0). На тесте это ловит карточки, дословно повторяющие обучающие.

Роутер ЛВ (`src/rules_lv.py`) — не список ключевых слов, а правила по механизму
товара. Хлопушка с вытяжным кольцом и шнуром — позитив, хлопушка пневматическая —
негатив; сухое горючее с тёркой для поджига — позитив, «вечная спичка» —
негатив; горелка в связке с газовым баллоном в названии — позитив, зажигалка-шокер
без топлива — негатив. Правило срабатывает только при непротиворечивом сигнале:
если нашлись и позитивный, и негативный признак, карточка остаётся модели.

Ответ собирается в формате соревнования: `id,result`, где `result` — строка
`<комментарий>…<вердикт>бан|не бан`. Предсказание 1 даёт вердикт «не бан», 0 —
«бан». Комментарий строится правилами: под категорию и вердикт подбирается первое
подходящее регулярное выражение, из текста карточки вырезается цитата ±25 символов
вокруг совпадения, и она подставляется в шаблон объяснения. Длина обязана лежать
в 50–300 символах. Готовая таблица валидируется той же регуляркой, что и у
организаторов; строки, не прошедшие проверку, пересобираются из нейтрального
шаблона. Формат ломает сабмит целиком, поэтому проверка стоит после генерации,
а не вместо неё.

Комментарий пишут правила, а не языковая модель, и это осознанный выбор. Причин
три. Формат жёсткий: 50–300 символов, генерация регулярно выходит за границы,
а нарушение обнуляет весь сабмит, тогда как шаблон укладывается всегда. Бюджет
инференса — 40 минут на прогон, из которых мультимодальная ветвь занимает 26;
на генерацию связного текста для каждого товара времени не остаётся. И главное:
модератору, который перепроверяет вердикт, полезнее дословная цитата из карточки,
чем пересказ — цитата проверяема и не может содержать выдуманной детали.
Классификацию при этом делают именно LLM и VLM, комментарий лишь предъявляет
улику, на которой основано решение.

## Два решения

Различаются не гиперпараметрами, а составом. Первое опирается на вторую LLM и
зрение, второе — на правила и retrieval поверх одной LLM.

| конфиг | состав | публичный скор |
|---|---|---|
| `configs/solution_1.json` | TF-IDF + LoRA Qwen3-VL-2B + LoRA Qwen3.5-4B + EVA-02 на ЛВ | 0.882858 |
| `configs/solution_2.json` | TF-IDF + LoRA Qwen3-VL-2B, роутер ЛВ, правило «не БАД», retrieval, dHash | 0.881965 |

Фактические доли ветвей и пороги первого решения:

| категория | tfidf | Qwen3-VL-2B | Qwen3.5-4B | EVA-02 | порог |
|---|---|---|---|---|---|
| БАД | 0.40 | 0.30 | 0.30 | — | 0.37 |
| Легковоспламеняющиеся | 0.10 | 0.15 | 0.35 | 0.40 | 0.41 |

В конфиге для ЛВ записано `adapter: 0.25`, `adapter_q35t: 0.5833` и `eva: 0.40` —
после умножения на `1 − 0.40` это и есть 0.15 и 0.35.

Второе решение проще: доли 0.50/0.50 в обеих категориях, те же пороги 0.37 и 0.41,
но включены `lv_router`, правило «не является БАД», dHash (для ЛВ только в сторону
позитива, для БАД в обе стороны) и точный retrieval по трём текстовым ключам.

Пороги ниже 0.5 в обеих категориях: F1 несимметричен к типам ошибок, недобор
полноты стоит дороже лишнего срабатывания. Значения взяты из конфига, а не
из pickle: сохранённый там OOF-порог относится к текстовой ветви в одиночку,
а решение принимает смесь.

Два решения намеренно устроены по-разному. Разница между ними — 0.0009 при sigma
дельты 0.018 (см. раздел про оценку), то есть на публичном сплите они
неразличимы. В такой ситуации осмысленно закрывать два разных класса ошибок,
а не отправлять два варианта одной конструкции.

## Подготовка данных

    ECUP_DATA=data ECUP_OUT=runs python src/prepare_data.py --folds 5 --seed 42

Скрипт считает md5 всех фотографий, склеивает товары в «семьи» через union-find по
двум связям — совпадению нормализованного текста и совпадению хэша фотографии — и
раскладывает по фолдам двумя способами: `fold_family` (StratifiedGroupKFold по
семьям) и `fold_iid` (обычный StratifiedKFold). Дубли в датасете есть, и без
группировки они разъезжаются между обучением и валидацией.

На выходе `families.pkl`, `imghash.pkl`, `labels_folds.csv` и `sft_data.jsonl` —
последний уже в формате обучения LLM: системные правила категории, текст карточки
(описание обрезано до 2500 символов) и пути к первым пяти фотографиям.

    ECUP_OUT=runs python src/build_image_cache.py --size 256

Кэш для визуальной ветви: каждая фотография вписывается в белый квадрат 256×256
через BICUBIC и складывается в memmap-массив uint8. Порядок файлов внутри товара —
сортировка по `(длина имени, имя)`. Тот же порядок и то же преобразование
воспроизводятся на инференсе в `src/eva_branch.py`; расхождение здесь тихо роняет
качество визуальной ветви, поэтому код преобразования продублирован дословно.

## Обучение

**Текстовая ветвь и индексы.**

    ECUP_DATA=data ECUP_OUT=runs ECUP_WEIGHTS=weights python src/train_text.py

Скрипт собирает `weights/model_v1.pkl` (44 МБ): словари и IDF обеих TF-IDF-матриц,
коэффициенты логрега по категориям, три текстовых индекса, индекс md5 фотографий,
голоса dHash по категориям и матрицу для нечёткого поиска по ЛВ.

На инференсе sklearn не используется: TF-IDF считается вручную в
`src/analyzers.py`. Поэтому при экспорте стоит проверка — ручное преобразование
сравнивается с `vectorizer.transform` на 200 карточках и обязано совпасть с
точностью 1e-9, иначе экспорт падает с assert. Расхождение между обучением и
инференсом здесь не заметно по логам и видно только по потере качества.

Порог, который печатает скрипт, считается OOF по `fold_iid` и потому оптимистичен
на дублях. В зачётных решениях он не используется.

**LoRA поверх Qwen3-VL-2B.**

    ECUP_DATA=data ECUP_OUT=runs ECUP_WEIGHTS=weights python src/train_lora.py \
      --base Qwen/Qwen3-VL-2B-Instruct --adapter-dir weights/adapter \
      --epochs 1 --batch 2 --grad-accum 8 --lr 1e-4 --lora-r 16 \
      --max-imgs 4 --max-pixels 262144 --max-len 3072 --lv-oversample 3 --val-fold -1

**LoRA поверх Qwen3.5-4B, только текст.**

    ECUP_DATA=data ECUP_OUT=runs ECUP_WEIGHTS=weights python src/train_lora.py \
      --base Qwen/Qwen3.5-4B --adapter-dir weights/adapter_q35t \
      --epochs 1 --batch 2 --grad-accum 8 --lr 1e-4 --lora-r 16 \
      --max-imgs 0 --max-len 2048 --lv-oversample 3 --val-fold -1

Обе ветви обучаются одним скриптом. LoRA ставится только на проекции языковой
части (`q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`
по маске `.*language_model.*`), визуальная башня заморожена: обучающих карточек
меньше тринадцати тысяч, и размораживать зрение на таком объёме нечем.
`r=16`, `alpha=32`, `dropout=0.05`, bf16, gradient checkpointing, косинусный
шедулер с прогревом 10% шагов. Позитивы ЛВ дублируются втрое.

`--val-fold -1` означает обучение на всей разметке — так собраны отправленные
адаптеры. Для оценки ветви тот же скрипт запускается с `--val-fold k`: он
скорит отложенный фолд и печатает F1 при 0.5 и лучший F1 с порогом по сетке.

**Визуальная ветвь.**

    ECUP_OUT=runs ECUP_WEIGHTS=weights python src/train_vision.py \
      --model eva02_base_patch14_224.mim_in22k --tag eva224 \
      --cats LV --folds 0,1,2,3,4 --size 224 --epochs 6 --bs 64 \
      --lr 1e-4 --llrd 0.75 --warm 0.25 --jpeg_p 0.5 --oversample_lv 8

Имя модели и `--tag` задавать обязательно: `src/eva_branch.py` создаёт архитектуру
`eva02_base_patch14_224.mim_in22k` и грузит веса по маске `eva224_LV_f*` со
`strict=True`. Дефолты скрипта другие, и с ними веса просто не встанут.

Аугментации считаются на GPU: случайный кроп через `affine_grid`, отражение,
яркость, контраст, насыщенность — и, отдельно, повторное JPEG-сжатие с
вероятностью 0.5 и качеством 40–95. Последнее не косметика: изображения в тесте
пересжаты организаторами, и модель должна быть устойчива именно к этому шуму.
Позитивы ЛВ дублируются восьмикратно, layer-wise decay 0.75, OneCycle. Веса
сохраняются в fp16 по фолдам.

## Инференс

    ECUP_CONFIG=configs/solution_1.json ECUP_WEIGHTS=weights \
    SHARED_MODELS_PATH=/shared_models \
    python src/predict.py --test_data_path data/test/data.csv --output_path predict.csv

Каталог с фотографиями берётся как `images/` рядом с `data.csv`. Базовые модели
в архив сабмита не кладутся — они берутся из `SHARED_MODELS_PATH` по списку
`model_candidates` (перебираются варианты регистра в имени каталога).

Ветви устроены fail-closed. Если заявленный в конфиге адаптер отсутствует в архиве
или не загрузился, `strict_adapters` и `strict_branches` роняют запуск с ошибкой.
Раньше отвалившаяся ветвь молча исключалась из смеси, веса перенормировались, и
сабмит уходил с другим составом, чем задумано, — разница видна только по скору
через сутки. Лучше упасть при запуске.

Строка `ВЕСА[категория] ЖИВЫЕ: tfidf=… adapter=… eva=…` печатается по факту
загрузки, а не по конфигу, и это первое, что имеет смысл читать в логе.

Сабмит собирается как самодостаточный каталог: `run.py` (копия `src/predict.py`
с плоскими импортами), `metadata.json` с образом и точкой входа, `v2_config.json`,
веса, адаптеры и вендоренные `peft` и `timm`. Собирается командой:

    python3 src/pack_submit.py --config configs/solution_1.json --out submit_1.zip

Готовые архивы в репозиторий не включены: они целиком собираются из его
содержимого и лишь дублировали бы веса.

## Как мы оценивали изменения

Разрыв публичного и приватного рейтингов на этой задаче оказался огромным. Лидер
публичного сплита с 0.9569 получил на приватном 0.8724 — минус восемь с половиной
пунктов. У нас 0.882858 на публичном и 0.867930 на приватном — минус полтора.

Причина понятна из данных: половина метрики — это F1 по классу с долей позитивов
3.6%, то есть по паре сотен объектов. Любая перестановка нескольких карточек
двигает скор сильнее, чем реальное улучшение модели.

Поэтому значимость каждого изменения мы оценивали парным бутстрапом по публичному
сплиту. Sigma дельты вышла 0.018. Правило было простое: изменение с приростом
меньше этого порога не отправляется, каким бы убедительным оно ни выглядело на
валидации. Оно и удержало решение от подгонки под публичный сплит — почти всё, что
давало «плюс» в третьем знаке, оказывалось шумом.

## Отрицательные результаты

**Текстовые энкодеры полным fine-tune как третья ветвь: −0.086 на лидерборде.**
Ветвь подмешивалась последовательно, поверх уже готовой смеси
(`p = (1 − e)·p + e·p_enc`), и при заметном `e` ужимала вес основной модели. Дело
не в том, что энкодер плох сам по себе, а в том, что он вытеснял более сильный
сигнал. Код ветви остался в `src/encoder_branch.py`, но в обоих зачётных конфигах
`enc_weights` не задан.

**Сильные визуальные модели дали примерно ноль.** Мы перебрали EVA-02, ViT-L,
SigLIP и DINOv2 и подняли AUC визуальной ветви на ЛВ с 0.895 до 0.968. В итоговой
метрике это не отразилось никак. Разбор показал причину: корреляция логитов
визуальной ветви с текстовым стеком — 0.63, тогда как у синтетического «оракула»
той же точности она 0.38. Зрение видит ровно то же, что модель уже прочитала в
описании. Ограничение не в качестве зрения, а в независимости ошибок, и наращивать
первое бессмысленно, пока не изменилось второе.

**Поиск дублей по фотографиям не работает на тесте.** Индекс md5 не даёт ни одного
совпадения, перцептивный dHash тоже не срабатывает: изображения в тесте пересжаты
организаторами. На обучающей выборке оба механизма выглядели полезными. В конфигах
они остались (`retrieval_img_cats`, `dhash_cats`): ничего не стоят и срабатывают
только при единогласии голосов. Вклада в скор не дали.

**Без значимого вклада также:** kNN по эмбеддингам мультимодальной модели (код
остался, `knn.enabled = false` в обоих конфигах), стекинг предсказаний ветвей,
признаки на основе OCR по фотографиям.

## Воспроизведение

Нужны исходные файлы соревнования — `data.csv` и каталог `images/`, — и базовые
модели `Qwen3-VL-2B-Instruct`, `Qwen3.5-4B`, `eva02_base_patch14_224.mim_in22k`.
Всё обученное лежит в репозитории: адаптеры, веса EVA по пяти фолдам и
`model_v1.pkl`. Заново обучать нужно, только если меняется код ветвей.

Базовые модели в репозиторий не включены: они публичные, весят около 13 ГБ и на
инференсе их отдаёт платформа через `SHARED_MODELS_PATH`. Для локального запуска
качаются штатными средствами:

    huggingface-cli download Qwen/Qwen3-VL-2B-Instruct --local-dir base/Qwen3-VL-2B-Instruct
    huggingface-cli download Qwen/Qwen3.5-4B --local-dir base/Qwen3.5-4B
    python -c "import timm; timm.create_model('eva02_base_patch14_224.mim_in22k', pretrained=True)"

После этого путь к ним задаётся переменной: `ECUP_BASE_MODEL=base` для обучения
или `SHARED_MODELS_PATH=base` для инференса. Ожидаемая раскладка каталога —
`<путь>/Qwen/<имя модели>`, как в окружении платформы.

Последовательность целиком:

    python src/prepare_data.py            # семьи, фолды, sft_data.jsonl
    python src/train_text.py              # model_v1.pkl
    python src/build_image_cache.py       # кэш 256x256
    python src/train_lora.py --base Qwen/Qwen3-VL-2B-Instruct ...
    python src/train_lora.py --base Qwen/Qwen3.5-4B ...
    python src/train_vision.py --cats LV ...
    python src/predict.py --test_data_path ... --output_path ...

Переменные окружения одинаковы для всех шагов:

| переменная | что задаёт | по умолчанию |
|---|---|---|
| `ECUP_DATA` | каталог с `data.csv` и `images/` | `data` |
| `ECUP_OUT` | промежуточные артефакты обучения | `runs` |
| `ECUP_WEIGHTS` | каталог с весами и адаптерами | `weights` |
| `ECUP_CONFIG` | конфиг решения для инференса | `v2_config.json` в корне репозитория, копия `configs/solution_1.json` |
| `ECUP_BASE_MODEL` | базовая модель для `train_lora.py` | `Qwen/Qwen3-VL-2B-Instruct` |
| `ECUP_NPROC` | процессы при построении кэша картинок | 8 |
| `SHARED_MODELS_PATH` | каталог базовых моделей на инференсе | `/shared_models` |

Порядок шагов жёсткий: `train_text.py` читает `families.pkl` и `imghash.pkl` от
`prepare_data.py`, `train_vision.py` — `labels_folds.csv` и кэш картинок.

## Зависимости

На инференсе версии фиксирует образ жюри — именно в нём решения проверялись
перед отправкой. `requirements.txt` в корне репозитория повторяет эти версии и
дополняет их тем, что нужно для обучения.

| компонент | версия | откуда |
|---|---|---|
| образ | `odsai/ecup26-quality-baseline:1.0` | `metadata.json` |
| torch | 2.10.0 | образ |
| torchvision | 0.25.0 | образ |
| transformers | 5.14.1 | образ, знает `qwen3_5` |
| peft | 0.20.0 | вендорится в `vendor/` архива |
| timm | 1.0.27 | вендорится в `vendor/` архива |

`peft` и `timm` вендорятся, потому что в базовом образе их нет либо версия не та.
Адаптер к 2B обучался под peft 0.19.1, адаптер к 4B — под 0.20.0; вендоренная
версия 0.20.0 поднимает оба, все ключи адаптеров встают на место.
Обучение дополнительно требует scikit-learn, scipy, pandas, Pillow, safetensors и
`qwen_vl_utils`; на инференсе scikit-learn не нужен.

## Лицензии

| компонент | лицензия | роль |
|---|---|---|
| `Qwen/Qwen3-VL-2B-Instruct` | Apache-2.0 | базовая мультимодальная модель |
| `Qwen/Qwen3.5-4B` | Apache-2.0 | базовая текстовая модель |
| `eva02_base_patch14_224.mim_in22k` | MIT | визуальная ветвь ЛВ |
| `peft` | Apache-2.0 | LoRA, вендорится в архив |
| `timm` | Apache-2.0 | загрузка EVA-02, вендорится в архив |

Обучаемые части посчитаны по файлам весов в репозитории, размеры базовых
моделей — по их карточкам:

| модель | параметров | обучалось |
|---|---|---|
| Qwen3-VL-2B-Instruct | 2 млрд | LoRA 17.4 млн (392 тензора, r=16) |
| Qwen3.5-4B | 4.54 млрд | LoRA 21.2 млн (256 тензоров, r=16) |
| EVA-02 base | 85.76 млн | полностью, 5 фолдов |

Требование к моделям в правилах конкурса сформулировано так: «Для решения
необходимо использовать LLM- и VLM-модели. Используемые модели должны иметь
открытую лицензию». Перечня конкретных моделей и порога по числу параметров
правила не содержат; на странице задачи ограничение названо как «малые (до 4B)
модели с открытой лицензией», то есть указан класс модели.

Обе базовые модели этому соответствуют: `Qwen3-VL-2B-Instruct` — VLM,
`Qwen3.5-4B` — LLM, обе под Apache-2.0. Отмечаем для полноты, что у `Qwen3.5-4B`
4.54 млрд параметров: это модель класса 4B, как её и публикует автор.

Обучение шло только на данных соревнования. Внешние размеченные наборы не
привлекались, дистилляция проприетарных моделей не использовалась, псевдоразметка
тестовой выборки не применялась.
